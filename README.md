# PingLab

A local Windows network doctor for gaming: it measures latency, jitter, loss, bufferbloat, DNS and Wi-Fi quality, explains what it finds, and applies a small set of **reversible** fixes. Every change is recorded before it is made and can be undone, and every claim is checked by reading the setting back from Windows rather than trusting a command that returned without error.

It runs entirely on your machine. The network traffic is the measurements themselves (your endpoint pings, DNS lookups, bufferbloat transfer) and one request at start-up: PingLab asks GitHub for the newest release tag, so it can tell you when a newer version exists. That request carries no identifier, and a check that cannot be made says nothing rather than claiming the copy is current. There is no telemetry, no account and no cloud.

## Installing it

Grab the newest release from <https://github.com/Mr-neiN/pinglab/releases>:

| file | what it is |
|---|---|
| `PingLab-Setup-<version>.exe` | per-user installer (no administrator rights needed to install) |
| `PingLab-<version>-portable.zip` | the same app, unzip and run `PingLab.cmd` |
| `SHA256SUMS.txt` | SHA-256 of both files |

The installer puts the app in `%LOCALAPPDATA%\Programs\PingLab`, adds **PingLab** and **PingLab terminal** to the Start menu (and optionally a desktop shortcut), and registers an uninstaller under *Settings → Apps*. It checks for Node.js 22+ before copying anything: if `node` is missing or too old it stops, says so, and offers to open the Node.js download page. Uninstalling removes the program and its shortcuts but leaves `data\` in the install folder, because that is where your restore points live — delete that folder yourself once no setting is left applied.

Installing never asks for elevation. Changing a setting still does — see [Administrator rights](#administrator-rights).

## Requirements

- Windows 10 or 11.
- **Node.js 22 or newer** for the terminal app and the local web UI (the run history uses Node's built-in `node:sqlite`).
- PowerShell 5.1, which ships with Windows, for the desktop GUI.
- A wireless adapter if you want the Wi-Fi rows; a machine without one shows those rows as "not applicable" instead of guessing.
- Location services enabled for your account if you want SSID/signal/channel detail on Windows 11. When Windows hides those fields, the web UI reports that reason and offers to open the Location settings page; elevation does not bypass it.
- Administrator approval (UAC) for each setting that changes something; a preset asks once per step it actually needs, and every step is a separate undo. Reading state never needs it. A standard (non-admin) account works: Windows asks for an administrator's credentials at that point, and the app tells you exactly how to proceed if that prompt is closed — see [Administrator rights](#administrator-rights).

## Launching it

Three surfaces, one engine (`lib/`) and one dispatch table for every action (`lib/tweaks.mjs`), so they cannot drift apart. The restore points and the per-area scripts that table calls live in `lib/backups.mjs`, `lib/tweaks-apply.mjs`, `lib/tweaks-tuning.mjs` and `lib/tweaks-wlan.mjs`, behind that facade.

| surface | how | notes |
|---|---|---|
| Desktop GUI | double-click `PingLab.cmd` | PowerShell WinForms; tabs for Overview, Fixes, Wi-Fi, Latency (latency and bufferbloat), DNS (benchmark table, shared verdict and winner) and Soak test. The Fixes tab carries all six settings, including DNS (benchmark, then use the winner, or go back to automatic) |
| Terminal | `PingLab-TUI.cmd`, or `node pinglab.mjs` | keys shown at the bottom of each view; `b` runs the bufferbloat test |
| Web UI | `node server.mjs` (or `npm start`) → <http://127.0.0.1:4747> | loopback only; every response is sent with a strict CSP and the API only answers the page it just served (per-run token, Origin and JSON checks) |

Every surface asks GitHub for the newest release when it starts, and says so — page banner, dashboard line, GUI status row — only when that release is newer than the copy you are running. The check is in the background, so no window waits for it; when GitHub cannot be reached, or no release has been published yet, nothing is claimed in either direction.

One-shot commands from a terminal:

```
node pinglab.mjs --once        render the dashboard once
node pinglab.mjs --view NAME   draw one dashboard view once (dash, fixes, probe, wifi, dns, soak, history)
node pinglab.mjs --fixes       list the reversible settings, their risk and their state
node pinglab.mjs --presets     the named presets and exactly what each applies
node pinglab.mjs --preset X    X = safe | latency (applies that preset)
node pinglab.mjs --audit       every managed setting vs what Windows/the driver reports
node pinglab.mjs --self-check  catalog, presets, dispatch and live state, changes nothing
node pinglab.mjs --wifi        channel and band diagnosis
node pinglab.mjs --probe       latency to the configured game endpoints
node pinglab.mjs --bloat       bufferbloat, download and upload
node pinglab.mjs --dns         DNS resolver benchmark
node pinglab.mjs --soak [min]  soak test, default 10 minutes
node pinglab.mjs --apply X     X = plan | nic | nagle | wifi | order | dns (dns benchmarks first and
                               writes the winner only; without a clear winner it leaves DNS alone)
node pinglab.mjs --revert X    undo that one setting
node pinglab.mjs --restore     restore everything PingLab changed
node pinglab.mjs --json        raw snapshot as JSON
```

In the terminal app, `f` opens the fixes view and `1`–`5` apply or revert one row, `S` applies the safe preset, `L` the lowest-latency preset, `R` restores everything. DNS lives in its own `d` view because choosing a resolver needs the benchmark first.

Which surface offers what:

| | plan | NIC | Nagle | radio | auto-connect order | DNS benchmark + apply |
|---|---|---|---|---|---|---|
| TUI | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ (`d` view) |
| GUI | ✓ | ✓ | ✓ | ✓ | ✓ | reads the current servers in Overview; no benchmark |
| Web | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

All three call the same `runTweakAction` dispatch table, and all three draw their names, descriptions, risk tags and preset lists from `lib/catalog.mjs`, so a row that exists on one surface exists on the others; the web UI has no separate allowlist of actions.

### The local API

The web server is one loopback port, and it treats every request as untrusted:

- **Token.** Every `/api/...` route — reads included — requires the per-run token the page was served with, in `X-PingLab-Token`. Missing or wrong is a 403 that says to reload; the comparison is constant-time, and a length mismatch is refused before the comparison so it cannot throw.
- **Origin.** Every `POST` must also carry this exact page's `Origin`, checked before the body is read, and must be `application/json`. A form on another site can therefore not reach a state-changing route at all.
- **Host.** A `Host` other than `127.0.0.1`, `localhost` or `[::1]` on this port is a 421 on every route. That is what stops a hostile domain pointed at loopback (DNS rebinding) from reading the page and its token.
- **Input.** Bodies are capped at 2 MB and must be JSON objects. Each value is checked where it is used: endpoint hosts and ports, the bufferbloat host, duration and direction, soak minutes and interval, DNS servers, the tweak action and adapter alias. A value that would be resolved, connected to or written into a script is refused when it is out of range, never silently clamped into something else.
- **Errors.** A refusal names the rejected field and nothing else; an internal failure is logged with the token redacted and answered with a fixed sentence, so parser text, file paths and stack traces never reach the browser. A request Node's own parser rejects gets the app's 400 with the same security headers, rather than Node's bare default.

## Settings you can change

Nothing here is applied at startup, and **every setting is off by default**: the `default` column below is checked by `--self-check`, so no future edit can quietly make one of them aggressive.

| setting | risk | what it changes | what it trades | undo |
|---|---|---|---|---|
| **Wireless power saving (power plan)** | safe | `powercfg` AC/DC index for *Wireless Adapter Settings → Power Saving Mode* set to `0` = maximum performance in the active power scheme. This is a scheme-level setting shared by **every Wi-Fi adapter**, not a per-adapter switch | *battery*: the radio stops stepping down to save power, so a laptop loses some runtime; *latency*: no more 10–50 ms spikes when the radio wakes mid-fight | the AC/DC values are written back to the **scheme they were recorded from**, even after a plan switch; a scheme Windows no longer has is reported, not rewritten. Restore-all also drops the per-scheme override when it matches the scheme default |
| **NIC power management (device)** | safe | `Disable-NetAdapterPowerManagement` for the adapter | *battery*: Windows can no longer park the device while idle; *stability*: removes the missed first packets after the card wakes. Many Wi-Fi drivers expose no such setting — the row then says "not available" instead of pretending | the setting is re-enabled, but only if PingLab was the one that disabled it |
| **TCP buffering and ACK timing (per adapter)** | **moderate** | `TCPNoDelay=1` (Nagle's send-side buffering off) and `TcpAckFrequency=1` (acknowledge TCP segments immediately instead of on the delayed-ACK timer) under `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\{adapter GUID}`. Two independent TCP values; neither affects UDP | *latency*: only TCP request/response traffic can gain — DNS lookups, downloads, voice chat and game logins. Most gameplay is UDP, where neither value does anything, so this is optional rather than a general gaming fix; *throughput*: more, smaller TCP segments and more ACK packets, which can cost bandwidth and CPU on a saturated uplink. This is not a global delayed-ACK switch | both recorded values are written back; keys that did not exist before are removed again. The row is done only when **both** read `1`, and a half-applied pair is shown as such |
| **Wi-Fi radio power save (driver properties)** | **experimental** | driver properties `MIMOPowerSaveMode=3` (No SMPS) and `RoamAggressiveness=0` (Lowest) — a hardware property, not a Windows preference | *battery*: both streams stay awake; *stability*: the card holds the current AP until the link drops (good with one router, bad on a mesh). Measured across repeated soaks here: **no gain**, which is why it is experimental and in no preset | the values the driver reported before the write are written back and verified |
| **Wi-Fi auto-connect order** | safe | `netsh wlan set profileorder` moves the profile of the network you are *currently joined to* to priority 1 | *stability*: after an adapter reset Windows rejoins that network instead of whichever saved network is first; the cost is that a deliberately different order is overridden until you restore | the exact previous precedence is replayed and read back; profiles deleted since are left out, never recreated |
| **DNS servers on this adapter** | **moderate** | `Set-DnsClientServerAddress` with the resolver that won the benchmark, or ones you type in | *page loads and sign-ins*: usually faster; *privacy*: queries go to the resolver you pick; *stability*: anything local in your router's DNS (Pi-hole, `.lan`/`.home` names, some captive portals) stops resolving unless you point at the router. Does not change in-game ping | the adapter goes back to DHCP-provided DNS when that is where its servers came from; a static DNS configuration is written back exactly as recorded. Both are read back, and *Restore everything* follows the same rule. |

**Which adapter they change.** Every setting above is read from, and written to, one adapter you choose. By default it is the adapter carrying the default route — the one whose traffic PingLab measures — but behind a VPN that route belongs to the tunnel's virtual device, so a physical adapter is chosen instead and the surface says so. The Fixes card has a picker, and so does the GUI's Fixes tab: physical adapters first, a virtual or VPN adapter only once you tick *show virtual / VPN adapters*, and choosing one is deliberate. The choice is saved in `config.json`, so the page, the GUI and the terminal all read and write the same device rather than each guessing from the routing table. Every row names the adapter it changes, and every restore point records the adapter it belongs to, which is what makes restoring one honest on a machine with more than one network port.

Risk levels mean:

- **safe** — one Windows setting, read back, one press to undo. It cannot strand the machine.
- **moderate** — reversible, but it changes behaviour beyond what PingLab measures (throughput shaping, local DNS), so read the trade before applying.
- **experimental** — no measurement here has shown a gain and it writes a hardware property. Never part of a preset; only applied by name.

There is exactly one setting I judged doubtful and kept only as an experiment: the Wi-Fi radio power-save row above. It was applied and soaked repeatedly on this machine and produced no measurable latency or jitter gain, so it is not offered as "tuning" and cannot be reached from any preset or bundled button. It stays in the list because it is fully reversible and someone with a specific adapter complaint may still want it — as a named, explicitly experimental choice.

## Administrator rights

Every setting above writes a machine-wide value, so Windows asks for administrator approval each time one is applied or reverted. Reads — the dashboard, `--fixes`, `--audit`, `--self-check`, the DNS benchmark — never need it.

| who | what happens |
|---|---|
| signed-in administrator | a consent dialog: click **Yes** |
| standard account | Windows asks for an administrator account and password (or PIN); approve it and the change runs under that account — nothing to install or configure |
| already elevated (e.g. *Run as administrator*) | no prompt at all, the action runs directly |
| prompt closed or refused | **nothing is written**; the setting is re-read and reported unchanged |

When the prompt does not go through, all three surfaces print the same sentence — built once in `lib/tweaks.mjs` (`elevationText`), so the GUI, TUI, web page and CLI cannot describe the same failure differently:

> Nagle's algorithm (per adapter) was not changed - the Windows administrator prompt was closed, so nothing was written. To do it yourself, right-click PingLab.cmd and choose "Run as administrator", or open an elevated PowerShell in the PingLab folder and run: node pinglab.mjs --apply nagle

An action that would change nothing (the setting is already in the requested state, or the adapter does not support it) says so before any prompt appears, so a standard account is never asked for credentials for a no-op.

The elevated script never touches disk. The app opens a private one-shot pipe, passes its random name to the elevated PowerShell, and sends the script text down it once that process has connected; the result returns on the same pipe and is accepted only with the nonce from that call. Up to 1.0.11 the script was written to `data\tmp\<id>.ps1` and that path was handed to Windows — a file the same user could replace between the write and the admin prompt, in which case the replacement ran with administrator rights. There is no such file to replace now, and a call that cannot open its pipe changes nothing rather than falling back to one.

Three test hooks make these paths checkable without clicking a prompt; none of them does anything unless the variable is set:

- `PINGLAB_ELEVATION=cancel` or `refuse` — every elevated call returns as if the prompt had been closed or refused, writing nothing.
- `PINGLAB_PS_STUB=<path to lib/ps-fake.mjs>` (+ `PINGLAB_PS_SCENARIO`, `PINGLAB_PS_LOG`) — replaces every PowerShell call with a fake Windows that answers the real scripts, used by `lib/tweaks.test.mjs` to exercise apply and revert without elevation.
- `PINGLAB_DNS_STUB=quad9` (any id from `lib/dns.mjs`) — the DNS benchmark returns a deterministic run where that resolver clearly wins, so the "write the winner" path can be proven on a network where the real resolvers are within noise.
- `PINGLAB_DATA_DIR=<folder>` — where restore points, history and transient files go. The tests point it at a throwaway directory, so a test run never touches the real data folder.
- `PINGLAB_BACKUP_DELAY_MS=<ms>` — pauses inside the locked restore-point write, so `lib/concurrency.test.mjs` can make two processes collide on purpose. It only widens the critical section; there is no retry hiding behind it.
- `PINGLAB_BACKUP_LOCK_WAIT_MS=<ms>` — shortens the wait for the restore-point lock, so the test can reach the honest "another PingLab action is writing restore points" failure.

## Presets

A preset is a short list of settings above, applied in order through the same rows, each with its own restore point and its own undo.

| preset | applies | leaves alone |
|---|---|---|
| **safe** / *Safe / recommended* | wireless power saving, NIC power management, Wi-Fi auto-connect order | Nagle (moderate), the radio experiment, DNS |
| **latency** / *Lowest latency* | the safe preset plus Nagle's algorithm | the radio experiment, DNS |

Rules the presets hold to:

- **Nothing experimental, ever.** `--self-check` fails if a preset lists a tweak marked experimental.
- **DNS is never changed by a preset.** Which resolver is fastest is a measurement, not a preset; it stays a separate button with its own benchmark rule.
- **Every step is separately undoable.** Each setting records its restore point before it is applied, so a preset is three or four individual changes, not one opaque one.
- **Nothing is hidden.** The result lists every step and what happened: applied, already in place, not available on this adapter, or failed.
- There is no bundled action that applies the whole list: presets replaced the old "apply every fix" button, and nothing can reach the experimental row without asking for it by name.

## What it deliberately only advises

These are never changed automatically, because the right answer depends on your hardware, your flat or your ISP:

- **Which DNS resolver to use.** The app measures and recommends; you decide. Only a resolver that answered **every** one of the ten probes can win: a resolver that dropped even one lookup is shown in the table with its missed count and is never offered, however low its median. Among the reliable ones a winner needs a median lead of at least 10% **and** wins at least 70% of the head-to-head probes. Otherwise the message says which resolver led and why that is noise (or which fast resolver missed lookups), and DNS is left alone.
- **Wi-Fi channel and band.** Co-channel and adjacent-channel interference, and which 5 GHz channels look free, are reported from the scan Windows returns, and every count is worded as a statement about that scan ("visible", "in this scan") rather than about the air. PingLab now also asks Windows for a scan itself: a small C# shim (`Add-Type`, `lib/wlan-shim.mjs`) calls `WlanScan` and waits for WLAN AutoConfig's `wlan_notification_acm_scan_complete` **before** reading `netsh`, so the result can say when the scan finished — "Windows confirmed a scan finished 412 ms after PingLab asked for one, and this list was read straight after" — instead of only reporting what `netsh` returned. That dates the scan, not every network in it, so it is still not a claim that each visible access point is live. The wait is bounded (6 s by default, clamped to 1–15 s) and the shim is optional: when it cannot be loaded, Windows refuses the scan (usually Location services off) or no completion arrives, the app falls back to the old behaviour — reads the list and says there is no confirmation, so **no fresh-or-cached verdict is claimed**. An earlier build guessed freshness from the number of visible networks: two or fewer meant "cached", so it opened the network flyout, waited, re-read, and withheld every count-based line. On a quiet two-network home that invented a stale scan; on a stale five-network list it said "refreshed" for a re-read it could not date. There is no such threshold any more, and freshness is never inferred from the list. Signal is called what Windows reports — a coarse quality percentage, not a speed — and the app never invents an adapter limit ("2x2, 20 MHz, 144 Mbps") or assumes which visible access point is your router. A channel both 5 GHz and 6 GHz use (36–177) whose `Band` line Windows omitted is reported as **unknown**, never as 5 GHz, and is counted in neither band.
- **A game's UDP latency, measured only where it can be measured.** PingLab sends up to ten small UDP probes to every game endpoint that resolved and publishes a query (stopping after three silent exchanges if the service never answers), on the same host and port as its TCP handshake, and reports their round-trip latency and loss next to the TCP and ICMP figures (an endpoint marked `none` publishes no query at all, so it is not probed and only its TCP handshake is measured). Each endpoint's probe speaks a real query where one exists, chosen by the endpoint's `protocol` field in `config.json`: A2S_INFO for Source Engine servers, `getinfo` for id Tech 3 (Quake III Arena, OpenArena, Enemy Territory — Quake Live speaks A2S instead), the RakNet unconnected ping for Minecraft Bedrock (and the other RakNet titles), the server-info query for Unreal Tournament 2004, Minecraft Java's GameSpy-style query (`enable-query`), and id Tech 4's `getInfo` (Doom 3, Quake 4, Enemy Territory: Quake Wars); otherwise a controlled echo whose payload carries a per-probe token. A2S servers that answer the first query with a challenge are asked again with it, and the exchange that returns the information block is the one timed; a challenge that is never followed by a block still counts as the service answering, at the challenge exchange's own round trip rather than a doubled figure. The challenge is only accepted at its exact size, a repeated identical challenge is not sent a third time, and every surface can say the answer came after a challenge — `challenged` is recorded on the UDP row and printed next to the figure. Only a reply that is that query's answer can become a figure, so the echo token, the Quake 3 challenge echo and the Bedrock timestamp all tie the answer to the packet this probe sent. It must also arrive from the exact address and port that was probed, after the query was handed to the OS: a datagram from another source is reported as `mismatched`, and a target datagram that predates the send or does not match the query as `unexpected`; neither is timed, received or counted as loss. A UDP figure proves that the service answered this probe, **not that the application port is fully functional** or that match traffic uses the same path; an ICMP “port closed” rejection is path evidence and is never a latency sample. UDP has no handshake, so a round trip exists only when the service answers the probe — then the average, jitter and loss mean exactly what they mean for TCP. Most game services ignore a packet they do not recognise and some firewalls drop UDP, so **no reply is reported as unanswered, never as 100% packet loss**; a host that answers “port closed” gives a path RTT, labelled as the network rather than the game. A TCP port that refuses connections while ICMP answers is reported as a blocked port, not a dead network; ICMP that never answers is reported as blocked, not as 100% packet loss. None of the three numbers is ever called “your game ping”. A UDP figure is the round trip of the query that service answered — not in-game ping, not the match server a round was played on, and not the packets a match sends; the same sentences say that on the page, in the terminal and in the GUI. Ten consecutive probes are enough to see jitter now, but not to characterise a line over an evening: the soak and the long-term trend are for the longer windows. The page, the terminal and the GUI now name them: the table and the handshake figures are the *network path* (TCP handshake, with ICMP as a cross-check), while the UDP row is the *game-server round trip* - a figure that exists only where that game answered its own query, and one that says so when a challenge handshake was needed.
- **Router-side settings** (QoS, SQM, band steering) and **ISP plans.** Out of scope by design; anything claiming a network speed-up from registry edits is not in this tool.
- **Windows Location services**, needed for Wi-Fi detail on Windows 11. The web UI can open the settings page for you; the app does not flip the switch.

## Undoing things

- **One setting:** press its key in the terminal, its button in the GUI, or its button in the web UI. The inverse is always derived from the stored backup, never from a default.
- **Everything:** `R` in the terminal, *Restore everything PingLab changed* in the GUI, `node pinglab.mjs --restore`, or the *Restore everything* button in the web UI. One elevation prompt restores every recorded setting to the values captured before PingLab touched them, then clears the restore points it has proven came back; the change history stays, so what was applied and reverted is still visible afterwards.
- If a restore does not read back as recorded (for example a profile was deleted in the meantime), the restore point is **kept** and the result says what disagreed, so you can retry rather than losing the original values.
- **A DNS restore point that does not say where its list came from is not guessed at.** Records written by the first builds hold only the servers, and the builds after them recorded the address's DHCP state as a stand-in, so a record can be genuinely ambiguous. The DNS row's undo and *Restore everything* leave that adapter alone, keep the record, and say so: handing the list to DHCP could discard a hand-set resolver, and writing it back as static could pin a router list that has since changed. `1.0.16` records the source directly, so this only applies to older records.
- **Verified, not assumed.** Every write is read back afterwards (registry values, `powercfg` indices, driver properties, DNS server list, the netsh precedence list). If the read-back disagrees, the change is reported as failed, not as done.
- **Checked again later, not only at the moment of the change.** A restore point records that PingLab changed a setting; the live state says what Windows reports now, and the two are compared. When something else puts a setting back — a Windows or driver update resetting NIC power management, a switch to another power plan (the record belongs to the scheme that was tuned), an adapter that comes back with a new GUID, DHCP handing the router's DNS back — the fixes view, the GUI's Fixes tab, the page and `--audit` say so with the same sentence, and applying that row again puts it back. Nothing is re-applied on its own, and a reading that cannot settle the question (a deleted Wi-Fi profile, an unreadable plan value, a DNS list neither side recognises) is reported as unknown instead of counted as drift.

Restore points live in `backups.json` inside PingLab's data folder — `%LOCALAPPDATA%\PingLab` for an installed copy, `data\` in a source checkout — and `node pinglab.mjs --audit` prints them under "restore points". A count of 0 means the machine is at its original values.

**One record, whoever writes it.** The terminal app, the GUI, the web page and a soak test can all be running at once, and they share one data folder. Every change to `backups.json` takes an exclusive lock (`.backups.lock`, created beside it), reads the file fresh under that lock, merges its own change and replaces the file atomically — so two changes landing together leave two restore points instead of one. A second action waits a moment for the lock; if it is still held, it says `Another PingLab action is writing restore points. Try again in a moment.` and changes nothing rather than overwriting the first. The history database runs in WAL mode with a busy timeout, and a write that still meets a busy database is retried, so two processes recording measurements at the same time both keep their rows; a database another process is merely writing is waited for, never set aside as damaged.

## Files it writes

The program folder is never written to, so an uninstall can remove it completely. Everything PingLab keeps lives in one data folder: `%LOCALAPPDATA%\PingLab` for an installed copy, `data\` beside the code in a source checkout, or wherever `PINGLAB_DATA_DIR` points.

- `config.json` — the endpoint list the latency test probes, and the adapter the settings are aimed at (`adapter`). Saving a new endpoint list keeps that choice, and choosing an adapter writes the endpoint list back unchanged; a file that cannot be used refuses the choice instead of being replaced with defaults. An endpoint may name the UDP query it is timed with (`protocol`: `a2s`, `q3`, `minecraft`, `minecraftjava`, `doom3`, `ut2004`, `echo` or `none`); any other value is refused by the same rule the page's save uses, an endpoint without one gets the controlled echo, and `none` says the service publishes no query so it is never sent a datagram. The built-in list ships four public game servers — TF2 (A2S), Quake 3, Minecraft Bedrock (CubeCraft) and UT2004 — each checked live with its protocol on 2026-11-25, plus five platform services (Riot/Valorant, Battle.net, Discord, Steam, Epic) that publish no query and are therefore marked `none` rather than probed with an echo nobody answers — Steam's legacy master-server query no longer answers and its replacement is the HTTPS Web API (already the handshake), Discord's UDP voice discovery needs a voice server from an authenticated API call, and Riot, Battle.net and Epic document no client-sendable query at all; they are other people's servers, so a row that stops answering is reported as unanswered and can be edited or removed, never treated as loss. It is checked on load with the same rules the page's save uses, so an endpoint the API would refuse cannot sit in the file and be probed. A malformed file, or one holding a value PingLab would reject, is not silently replaced by the built-in list: the reason appears on the page, in the GUI's status row, at the top of the terminal dashboard and in `/api/state`, its bytes are kept beside it as `config.corrupt-<time>.json`, and the app runs on the built-in endpoints until a new list is saved.
- `backups.json` — restore points and the change history. Each apply saves its restore point here *before* Windows is touched, and the file is replaced atomically (written to a temporary file, flushed, then renamed), so an interrupted write leaves the previous restore points intact. Keep it if you have changes applied. If it is ever unreadable, PingLab treats its contents as unknown rather than empty: nothing is applied or reverted, the original is never overwritten, a copy is kept as `backups.corrupt-<time>.json` beside it, and `--audit`, `--self-check`, the fixes view and the GUI all say so.
- `pinglab.sqlite` — probe, DNS and soak history. It runs in WAL mode, so while it is open Windows also shows `pinglab.sqlite-wal` and `pinglab.sqlite-shm` beside it. If it is ever unreadable (not a database at all), PingLab starts anyway: the file is moved aside as `pinglab.corrupt-<time>.sqlite`, an empty database takes its place, and the terminal dashboard, `--audit`, `--self-check`, the GUI's status row and the web page all say so instead of the app dying at startup.
- `bridge-out.*.jsonl`, `.backups.lock` — transient files used by the GUI bridge and the restore-point lock. The lock exists only while a change is being recorded. A `tmp\` folder is only leftover scratch from a version before 1.0.12, whose elevated calls ran a script file from there; current versions write no file for elevation.
- `gui.log` — the GUI's start-up log.

An upgrade replaces programs only, so all of this survives it. A copy installed before 1.0.3 kept these files in `<install>\data`; the first run copies the restore points and the database into the per-user folder, deletes the transient files that folder had accumulated, and then removes the folder itself — so restore points survive the upgrade, nothing is left stranded in the install folder, and an uninstall can remove that folder completely. Uninstalling leaves the data folder in place: it is your record of what the machine looked like, not program files.

Deleting the database resets history; deleting `backups.json` while changes are applied means PingLab can no longer undo them.

## Development

- `npm test` runs every suite through `scripts/run-tests.mjs`, the same list CI and the release job run, and `npm run verify` runs that plus the static checks. `npm run lint` parses every JavaScript and PowerShell file and checks that each element id `public/app.js` looks up exists in `public/index.html` - a renamed element is not a syntax error, it is a dead button, and no parse check would notice. `npm run perf` starts the real server against the fake Windows and prints `/api/state` (cold and warm), `/api/benchmark` and `/api/probe` timings, plus probe overhead against a bare TCP handshake; CI runs it with `--check`, where only a read many times slower than the wide ceilings fails the job and the numbers are printed either way.
- `lib/catalog.mjs` is the single description of every setting: label, what it changes, what it trades, risk, Windows default, how it is undone, which preset includes it. The TUI, the GUI and the web UI all render from it — add a setting there and each surface picks it up. `validateCatalog()` enforces that every entry has a description, a trade-off, a risk, an undo and `default: "off"`, and that no preset contains an experimental setting.
- `lib/target.mjs` is the rule for which adapter a setting is aimed at, and it is pure: the adapter list, the default routes and the remembered name go in; a target, the choices a picker may offer and the sentences explaining a fallback come out. The default route is preselected, a virtual or VPN adapter is never picked on its own, a remembered adapter wins even when it is virtual, and one that has left the machine falls back with a sentence. `lib/adapter-pick.test.mjs` pins those rules, then proves the rest of the chain against the real server and the shipped page: the choice is saved in `config.json` (and survives an endpoint save), `/api/adapter` refuses a name the machine does not have without writing anything, the picker preselects the target and hides virtual adapters until asked, every row and every restore point names the adapter, and a row's apply posts the chosen adapter — run it with `node lib/adapter-pick.test.mjs`. The desktop window has the same picker, and `lib/gui-adapter.test.mjs` proves it by building the real WinForms window without showing it: it preselects the default route's physical adapter over a VPN tunnel and shows the same note, hides virtual adapters until the box is ticked, saves a choice through the bridge command the page's route also uses, re-reads the rows and restore points against it, and refuses an unknown name without touching the saved choice — run it with `node lib/gui-adapter.test.mjs` on Windows.
- `lib/config.mjs` is the one persisted file of settings: the endpoint list the latency test probes and the adapter the settings are aimed at. It is validated on load with the API's own rule (`endpointList` in `lib/api-input.mjs`), not a second copy of it, so a file edited by hand or cut short by a crash cannot add an endpoint the probe would refuse. A file that cannot be used is reported on every surface instead of being replaced by the built-in list, and its bytes are kept as `config.corrupt-<time>.json`; the next save says so as well, rather than replacing the old file without a word. `lib/config.test.mjs` pins the reported load, the kept copy surviving that save, save-side validation, and the report arriving through the real server's `/api/state` and `/api/endpoints` — run it with `node lib/config.test.mjs`.
- `lib/tweaks.mjs` is the single dispatch table (`runTweakAction`) plus `applyPreset` and `restoreAll`, which walk a preset and the restore points through that same table; it re-exports the public names (`tweakState`, `backupStatus`, `readBackups`, `writeBackups`, `dnsSourceOf`) so callers did not have to change. `lib/backups.mjs` owns `backups.json` (reading, the lock, restore points, the change history), `lib/tweaks-apply.mjs` the state read and the DNS/power/Nagle scripts, `lib/tweaks-tuning.mjs` the adapter-property script, `lib/tweaks-wlan.mjs` the Wi-Fi profile order, and `lib/tweak-shared.mjs` the quoting, DNS-source and elevation-refusal helpers more than one of them uses. `lib/tweaks.test.mjs` drives `runTweakAction`, `applyPreset` and `restoreAll` against `lib/ps-fake.mjs` (a fake Windows loaded through `PINGLAB_PS_STUB`) and pins applied / already-in-place / unavailable / refused / failed-after-write / reverted / restored, including the restore point each one leaves behind — run it with `node lib/tweaks.test.mjs`. `lib/tweaks-split.test.mjs` fingerprints every multi-line PowerShell template in the pre-split file and requires the modules to still contain exactly those bytes, then runs an apply, its revert and a restore-all across the new boundaries — run it with `node lib/tweaks-split.test.mjs`.
- `lib/state-cache.mjs` is the short-lived cache in front of `GET /api/state`. A state read pays for several PowerShell processes and the settings change only when someone acts, so a repeat within five seconds is served without reading the machine; after that the old value is served once while one background read refreshes it, and beyond two minutes the read is awaited. Every apply, revert, restore, probe, endpoint save and soak action invalidates it, and a read that started before a change can never install its old answer. `lib/state-cache.test.mjs` proves the fresh hit (with zero PowerShell calls), the TTL refresh, single flight, and — running the real server against a file-backed fake Windows — that applying a tweak is reflected by the very next state read; run it with `node lib/state-cache.test.mjs`.
- `node pinglab.mjs --self-check` is the check to run after touching any of this: it validates the catalog and presets, compares every catalog action against the dispatch table, reads each setting from Windows, and compares the app's claim with what Windows reports. It exits non-zero on any disagreement, and changes nothing.
- `node pinglab.mjs --audit` is the same comparison with more detail per row.
- `lib/backup-lock.mjs` is the one lock around `backups.json`: an exclusive-create file with a bounded wait, a stale lock broken only when its owner is gone or it has outlived any plausible write, and a release in a `finally`, so a write that fails cannot leave the file locked. `lib/concurrency.test.mjs` spawns two real child processes that start through a barrier and asserts that both restore points survive, that a blocked worker gets the lock sentence and changes nothing, that two processes inserting soak samples both keep every row, and that a `backups.json` written by 1.0.10 loads unchanged — run it with `node lib/concurrency.test.mjs`. The atomic replace retries a brief Windows sharing violation (`EPERM`/`EBUSY`/`EACCES`) for up to a second, because a reader in another surface can otherwise make a correct write fail; a lock that stays held still fails with the honest sentence.
- `lib/api-input.mjs` is the API's validation layer, and `lib/api-hardening.test.mjs` walks the whole HTTP surface the way an attacker would: every route without a token and with a wrong one, every POST with a missing or foreign Origin and a non-JSON body, every route with a foreign Host, unexpected methods, malformed and `null` and oversized bodies, 40-endpoint lists, option-shaped hosts and durations, traversal attempts, and a malformed request line — plus the page, its asset and its normal calls, so hardening that breaks the app fails the test. `lib/api-input.test.mjs` pins the boundaries of each rule. Run them with `node lib/api-input.test.mjs` and `node lib/api-hardening.test.mjs`.
- `lib/elevation-channel.mjs` is how an elevated script reaches administrator PowerShell: a named pipe this process owns, the script sent as a length-framed UTF-8 message once the elevated side has connected, and the result returned on the same pipe with a per-call nonce. Nothing is written to disk, so there is no path to replace between writing and elevation. `lib/elevation-channel.test.mjs` runs the real bootstrap through `powershell.exe` without the UAC hop and pins that the script never appears as a file, that a planted `.ps1` / `.out.json` in the data folder is never run or read, that a missing channel fails closed, and that another call's result is discarded — and it runs the shipped `Start-Process` launcher line from `lib/ps.mjs` itself, with only the UAC verb removed, so the arguments a real administrator prompt receives are the ones the suite exercised (1.0.18 passed the base64 bootstrap without `-EncodedCommand`, so PowerShell read it as a command name and every elevated change failed) — run it with `node lib/elevation-channel.test.mjs`.
- `lib/db.mjs` owns the history database and the rule that a damaged one is never fatal: it moves the file aside, starts a fresh one and reports it through `dbStatus()`. It opens in WAL mode with a busy timeout and retries a write that still meets a busy database, so a second process recording a soak cannot lose a sample; a database another process is merely writing is waited for, never moved aside as damaged. `lib/db.test.mjs` feeds it a text file where the database should be and pins that every surface can still start, write and read history, and that a second run with the same bytes reuses the copy — run it with `node lib/db.test.mjs`.
- `lib/db-warning.test.mjs` starts the real `server.mjs`, the GUI's bridge and `node pinglab.mjs --once` against a data folder holding a text file where `pinglab.sqlite` belongs, and requires `/api/state`, the bridge's `state` answer and the rendered dashboard to report it — those are what the page, the status row and the terminal draw from, so the warning cannot disappear from a normal start-up path again. Run it with `node lib/db-warning.test.mjs`.
- `lib/drift.mjs` compares the restore points with the live state and names a setting PingLab changed that Windows has since put back — with one sentence every surface prints, because the terminal, the GUI's Fixes tab, the page and `--audit` draw it from here. `lib/drift.test.mjs` drives it on the fake Windows: reverted, in place and unknown for every setting, plus a switched power plan that is still at maximum (not drift), a changed adapter GUID and a DNS list somebody else chose — run it with `node lib/drift.test.mjs`.
- `lib/keep-unreadable.mjs` is the one rule for putting a file that cannot be read aside: `<name>.corrupt-<time><suffix>` beside it, one copy per distinct broken file, and a file another instance has locked reported instead of worked around. `lib/db.mjs` uses it in move mode (the name has to be free for the fresh database), `lib/tweaks.mjs` in copy mode (a broken `backups.json` is never overwritten).
- `lib/one-line.mjs` is the one rule for text that reaches a terminal or a log line: control characters (a Wi-Fi SSID is written by whoever runs the access point) become a visible `?`, so no beacon can clear the screen, move the cursor or forge a line, while emoji and accents stay as they are. It is applied where Windows text enters (`lib/net.mjs` for the SSID, `lib/tweaks.mjs` for profile names) and to the endpoint labels the API accepts.
- `lib/dns.mjs` holds the resolver benchmark and the verdict rule, including the reliability gate: only a resolver that answered every lookup is rankable, and a faster resolver that missed one is named in the verdict rather than quietly promoted. `lib/dns-verdict.test.mjs` drives the reliability, noise, tie and 10% / 70% boundaries with fixed inputs — run it with `node lib/dns-verdict.test.mjs`.
- `lib/probe.mjs` turns raw round-trips into the figures every surface prints. Its UDP classifier admits only a datagram from the probed address and port, after the probe's own send, whose payload passes the protocol matcher; wrong source, wrong payload, ICMP rejection and timeout each have a separate outcome and stage. Jitter there is the mean absolute difference between *consecutive* samples, measured before anything is sorted; `lib/probe-math.test.mjs` pins that order along with loss, the percentiles, the ICMP latency/jitter cross-check, the blocked-ICMP distinction, and the UDP rule that only an answered probe may become a latency or loss figure (silence and a closed port never do, and the closed-port path figure is kept out of both) — including a live loopback echo and a closed loopback port over real UDP sockets. The queries and their reply matchers live in `lib/udp-proto.mjs` (pure, no sockets), and the same suite pins that an A2S challenge is answered with a second query, that only the info block counts as the answer and a reply longer than a four-byte challenge is not treated as one, that the Minecraft Java session id and challenge must both come back, that the Doom 3 reply must carry the engine's `infoResponse` header and `si_version`, that an unrelated datagram is reported as `unexpected` and never becomes a latency, and that the Minecraft Bedrock, UT2004 and Quake 3 matchers accept only their own replies. A row that names `none` is never sent a datagram: it carries `state: "no-query"`, `sent: 0` and no latency or loss, so a platform service cannot be read as a game server that stayed silent. `lib/udp-live.test.mjs` then runs every protocol end to end over real UDP sockets: one loopback server per wire format, including an A2S port that challenges before it answers, a Bedrock port that echoes the timestamp it was sent, and a Java port that checks the session id it was given, plus the two outcomes that must never be timed (a port that stays silent, and a closed port). With `PINGLAB_LIVE=1` the same suite probes the four public game servers shipped in the defaults, asserting only that an answered row has a finite latency and a silent one has neither a latency nor a loss figure — run it with `node lib/udp-live.test.mjs`, or `PINGLAB_LIVE=1 node lib/udp-live.test.mjs` on a machine with internet. Run it with `node lib/probe-math.test.mjs`. `lib/bufferbloat.mjs` owns bufferbloat in three modes (`down`, `up`, `both` sequentially, `duplex` at once); `lib/bufferbloat.test.mjs` runs the real download and upload saturators against a local HTTP server, including a blocked upload that must report "not measured" instead of a grade — run it with `node lib/bufferbloat.test.mjs`.
- **Long-term latency and jitter.** Each latency run is stored in `runs` with its summary, so the page's latency card can show what the last runs said instead of only the previous one: `lib/trend.mjs` reads the stored probe runs oldest-first, keeps only runs where a game service actually answered (silence is not a sample), and states a direction from the earlier half against the later half - never from the newest run against the one before it. Fewer than four stored runs produce the count and the median, not a trend. `/api/state.trend` carries the points and the one sentence every surface can print, and the page draws them as a sparkline under the table. `lib/trend.test.mjs` pins the empty, single, below-threshold, half-split, unanswered-run and jitter cases - run it with `node lib/trend.test.mjs`.
- **One version, everywhere.** `package.json` is the only place the version is written down: the release workflow refuses a tag whose number differs from it, `installer/build.ps1` refuses a build whose `-Version` differs from it, the installer includes the generated `version.iss` instead of restating a number, and the start-up update check compares releases against it. The page's top bar now shows that version (from `GET /api/state`) and so does the terminal dashboard's title, so an upgraded copy and a stale one can be told apart at a glance instead of inferred. `lib/version.test.mjs` pins the chain — the parsed version, the API agreeing with `package.json`, the installer having no numeric version of its own — and then runs the real `installer/build.ps1` at a different version and asserts it exits non-zero before writing anything, run it with `node lib/version.test.mjs`.
- `lib/update.mjs` is the start-up version check: it reads the version from the `package.json` beside it, asks `api.github.com/repos/Mr-neiN/pinglab/releases/latest` once per run, and compares tags numerically, so `1.0.10` is newer than `1.0.9`. Only a newer release produces a sentence, and a check that fails (offline, no release yet, an unreadable answer, a 4-second timeout) produces `checked: false` and no sentence instead of a false "up to date"; the server, the dashboard and the GUI bridge all carry that same answer. `lib/update.test.mjs` pins the comparison and every failure with a stubbed fetch, then starts a real server against a loopback releases stub and reads the sentence out of `/api/state` - run it with `node lib/update.test.mjs`.
- `lib/report.mjs` is the single source for the sentences and selectors more than one surface prints: the DNS winner and verdict, the bufferbloat grade meaning, the TCP-versus-ICMP explanation and the UDP sentence that keeps a service round-trip, a closed port and silence apart. `lib/report.test.mjs` pins them, so the page cannot offer a resolver the rule refused or read a field the benchmark never produced — run it with `node lib/report.test.mjs`.

- `lib/http.mjs` owns how every answer is written (security headers, JSON and text replies, the constant-time page-token check, the JSON body reader); `lib/static-site.mjs` serves `public/` and is the one place `index.html` learns the run's token; `lib/app-state.mjs` assembles the `/api/state` object and the benchmark policy. `server.mjs` is left with the routes and the run loop, so a header or a state field is changed once instead of inside a route.
- `lib/tui-format.mjs` holds the terminal palette, the escape-aware column padding, the number/time helpers and text wrapping. `lib/tui-views.mjs` draws the eight dashboard views and the adapter picker, and `lib/gui-bridge.mjs` is the line-delimited JSON protocol the desktop window drives; `pinglab.mjs` keeps the shell (argument parsing, key handling, `render`, `main`). `lib/tui-render.test.mjs` runs `node pinglab.mjs --once` against the fake Windows and requires the title, overview, connection box and footer — run it with `node lib/tui-render.test.mjs`. The DNS tab and the Fixes row call the same bridge `dns` command, and `lib/gui-dns.test.mjs` runs the real window headless against the deterministic resolver stub and requires the GUI's table, verdict and winner to equal the page's `POST /api/dns-bench` answer and the TUI's `viewDns` rendering — run it with `node lib/gui-dns.test.mjs` on Windows. The page is five classic scripts loaded in order — `public/core.js` (state, API helper, formatting), `probe-view.js` (latency, trend, bloat and DNS rendering), `fixes-view.js` (adapter picker, fix cards, notices), `bench-view.js` (before/after panel) and `app.js` (actions, endpoint editor, soak, wiring) — and `scripts/static-check.mjs` checks element ids across all of them.
- `lib/bench.mjs` is the before/after rule. A tweak that reads back as applied has proved only that Windows accepted a value, so the page's Before / after card measures seven full latency runs with the current endpoints, asks you to apply exactly one setting, then measures seven more with the same endpoints and sample count. Each phase is summarised by the median of its repeats and the range (max - min) of those repeats, and a metric is called improved or regressed only when the difference is strictly larger than the wider phase's range or the per-metric floor, whichever is larger, so a 1 ms move on a stable line is reported as within noise. A game endpoint is compared over its UDP query when every repeat answered it (A2S_INFO, Quake 3 info or a controlled echo) and over the TCP handshake otherwise, with the fallback recorded as a note; the transport is part of the comparison's parameters and of its sentence, so a baseline measured over UDP is refused against an after-run measured over TCP rather than mixed with it. `BENCH` holds the policy (`repeats`, `minRepeats`, `count`, `floors`) — each phase now runs seven repeats rather than five, so the noise band is estimated from more of what the line actually did, and the page quotes that number from `/api/state` rather than repeating it in its own copy. Raising `repeats` further buys a better noise estimate for more measurement time. Too few repeats, a repeat that lost an endpoint, or two phases measured with different endpoints or sample counts are reported as insufficient or refused with a reason instead of a delta, and a baseline older than `maxAgeMs` (30 minutes) is refused as well, because a measurement taken later is a different condition. The comparison is stored as a `benchmark` run with both phases' samples, and rolling it back goes through the same dispatch table every other undo uses, only after the page asks; the stored answer records what was restored and what is still pending. `lib/bench.test.mjs` pins the verdict boundaries, the floor, insufficient data and the refused comparisons, then drives the real server through baseline, apply, compare and an approval-gated rollback - run it with `node lib/bench.test.mjs`. `lib/bench-ui.test.mjs` then loads the shipped page itself into a `node:vm` DOM against a real server and clicks the card through baseline, apply, measure, the rendered table and a confirm-gated rollback, checks the reload rehydration and the insufficient-data rendering, and checks that `/api/state`, the terminal dashboard and the GUI's bridge response report the comparison and the rollback outcome including what is still applied - run it with `node lib/bench-ui.test.mjs`.
- `installer/build.ps1` builds the release artifacts into `dist/`: the portable zip, the Inno Setup installer (`installer/pinglab.iss`, per-user, Node checked in `[Code]`) and `SHA256SUMS.txt`. It picks the version from `package.json` unless you pass `-Version`. `installer/write-checksums.ps1` is the one writer of that `SHA256SUMS.txt`, used by the build and again by the release job after signing, so the published hashes describe the signed installer rather than the bytes that existed before signtool ran; `installer/verify-release.ps1` reads them back and refuses a release whose hashes do not match. The icon comes from `installer/make-icon.ps1` and is committed, so a normal build does not redraw it.
- `.github/workflows/release.yml` builds and attaches those files to a GitHub release for every tag shaped like `v1.2.3`, or on demand for an existing tag. The tag's version is passed to `build.ps1`, so the installer, the zip and the release all carry the same number, and both the workflow and `build.ps1` refuse a tag whose version differs from `package.json` — the app reports its version from that file, and its start-up update check compares it with the newest release, so a copy that called itself older than it is would be wrong on every launch.
- `.github/workflows/ci.yml` runs the whole suite on a `windows-latest` runner for every push to `main` and every pull request, because these tests drive PowerShell, netsh and the registry through `lib/ps-fake.mjs` and a Linux runner would prove nothing about them. `node scripts/run-tests.mjs` runs the same list locally (`node scripts/run-tests.mjs config` for one file's suites) and the release workflow calls it too, so a suite cannot be listed in one place and forgotten in the other. After the build, `installer/verify-release.ps1` re-hashes every artifact and refuses to publish when `SHA256SUMS.txt` disagrees with the bytes on disk or leaves a `.zip`/`.exe` out. The job runs the same static checks and suite as CI. Signing is opt-in: with repository secrets `SIGNING_PFX_BASE64` (a base64 PKCS#12) and `SIGNING_PFX_PASSWORD` set, the installer is signed with signtool, the signature is verified with `Get-AuthenticodeSignature`, `SHA256SUMS.txt` is regenerated from the signed bytes and only then is the release published; without them the artifacts ship unsigned and the log says so.

## Limits

- Windows only, and localized `netsh` output is parsed — the profile list is found by its dashed section headers rather than by English keywords, but unusual formats make the row refuse to act instead of guessing.
- The auto-connect row needs a wireless adapter, at least one saved profile and a current connection; with no profiles, no joined network, or no profile matching the SSID it says exactly that and changes nothing. If a profile recorded in a backup has since been deleted, restore leaves it out rather than recreating it.
- One UAC prompt per setting; a preset asks once per step it needs. A dismissed prompt is reported as "nothing changed", never as success, and stops the remaining steps instead of asking again.
- The bufferbloat test needs Cloudflare's speed-test endpoint for downloads and uploads. If a network blocks it, that direction reports "not measured" with the reason instead of grading an idle line.
- No installer, no license file, no telemetry. Copy the folder, install Node, run it.
